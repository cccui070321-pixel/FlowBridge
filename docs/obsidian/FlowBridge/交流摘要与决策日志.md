# 交流摘要与决策日志

本文不是逐字聊天记录，而是把项目交流中会影响产品和研发的内容整理成可追溯决策。

## D-001 第一版必须可公开获取

- 决策：代码与 Windows 安装包发布到公开 GitHub；
- 原因：不仅自己使用，还希望其他用户可下载，并用于小红书宣发；
- 影响：每个公开版本需要 Release 页面、安装包、升级说明和校验值。

## D-002 功能分支保留

- 决策：发布 v0.2.0 时允许合并与发布，但保留功能分支；
- 影响：后续 v0.3 系列继续在 `agent/v0.3-product-upgrade` 上演进。

## D-003 Supabase 作为第一阶段云端

- 决策：使用 Supabase Auth、Realtime、数据库与 Storage；
- 原因：能较快完成同一账号下的双机同步；
- 约束：必须依赖 RLS，客户端只使用 Publishable key。

## D-004 默认手动发送

- 决策：自动剪贴板同步与自动写入默认关闭；
- 原因：避免密码、验证码、公司内容在用户不知情时上传；
- 用户可主动开启，并随时暂停同步。

## D-005 第二阶段重点是产品化，而不只是加功能

- 用户反馈：原界面字太小、密度高，希望像苹果一样简单、规整；
- 决策：建立更大字号、留白、统一卡片、浅色/深色与自定义设置；
- 同时增加个人主页、存储与管理后台，让产品具备长期运营能力。

## D-006 管理员可运营，但不能默认读取正文

- 决策：管理员可以管理账号、设备、配额、传输元数据和审计；
- 默认不能查看剪贴板正文、Prompt 正文和文件内容；
- 内容访问若以后开放，需要限时支持模式、明确原因和审计。

## D-007 文件上限目标保持 500MB

- 平台限制：Supabase Free 单对象 50MB；
- 决策：不立即要求付费升级，通过 45MB 多对象分片实现产品层 500MB；
- 代价：客户端必须管理清单、合并、清理与校验。

## D-008 内部路径与用户文件名分离

- 决策：Storage key 只使用安全 ASCII 名称；
- 原文件名作为业务元数据保存；
- 原因：支持中文文件名并避免 URL/path 注入与兼容问题。

## D-009 旧失败记录不能假装可重试

- 当前按钮只改变状态时，不能称为真正重试；
- 后续必须在本地文件不可访问时引导用户重新选择；
- 所有错误信息要告诉用户“下一步怎么做”。

## D-010 近期优先级

1. 真实双机端到端验收；
2. 传输稳定性和错误可读化；
3. 软件内版本检查与更新入口；
4. 再考虑局域网直连、团队协作和 AI 自动分类。

## D-011 v0.4.0 以可靠性为发布主线

- 用户反馈：一台电脑可发送但另一台经常漏接，连接会短暂失效；
- 决策：不再把 Realtime 通知视为唯一送达通道，增加自动重连、定时补拉、幂等处理和接收确认；
- 发布标准：必须在两台真实 Windows 电脑上双向通过断网、睡眠、重启与大文件测试。

## D-012 自动更新使用 GitHub Release

- 决策：v0.4.0 接入程序内自动更新，继续使用官方公开 GitHub Release，不新增独立更新服务器；
- 过渡：由于 v0.3.3 没有更新模块，需要最后手动安装一次 v0.4.0；
- 之后：从 v0.4.0 开始，检查、下载、校验和安装均在程序内完成。

## D-013 关闭窗口默认缩到系统托盘

- 原因：接收端退出程序后无法实时收到文件，容易被误认为连接故障；
- 决策：默认后台运行，用户仍可从托盘彻底退出；
- 退出前有进行中任务时必须提示。

## D-014 头像壁纸与无效按钮

- 头像和壁纸由用户上传，账号内多设备同步；
- 所有可见按钮必须执行真实动作；
- 工作空间假下拉改为信息卡，铃铛实现通知中心，`Ctrl K` 真正聚焦搜索；
- 文件重试和清理必须作用于真实任务与数据。
